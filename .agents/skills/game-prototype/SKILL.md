# Game prototype

The actual task decides what to build, how to submit it, and whether to present it. In Garena R4, use Codex on the provided Windows machine to deliver an interactive HTML page. Default to one `prototype/index.html` with inline CSS and JavaScript that opens in Edge or Chrome by double-click, without a runtime, server, or deployment. Browser research and optional media are allowed. The core flow should work when media or the network is unavailable. Use the task's UI language, or Simplified Chinese when unspecified.

## Start from the chosen concept

- Read `prototype/BRIEF.md`. If it has a moment card, build that idea and keep its screenshot moment as the first priority after the main path. If there is no brief, write a short one from the task with the fields listed in `AGENTS.md`, plus the player and moment, the player's verb, the AI's role if any, and the demo click path. Keep the statuses current: 已实现 when built, 已验证 only after a check on the real page. Tell the user that `$game-brainstorm` can widen the options, and don't run a brainstorm yourself.
- Continue straight into implementation. Ask only when a missing decision would materially change the deliverable and cannot be inferred. Prefer one mechanic that changes what the player can do. A reward, animation, or chat panel earns its place when it serves that mechanic.
- For the edge state and measure that fit the brief type, see [feature patterns](../game-brainstorm/references/feature-patterns.md). Treat invented numbers as demo data or hypotheses, and verify any real-world claims you include.
- `prototype/IDEAS.md`, if present, holds parked ideas. Use it when the user asks for a wow moment or an extra feature.

## Build the shortest working path

- Aim for an interactive `index.html` in the first 30–45 minutes. The first build turn is done when a fresh load shows the starting state, the main action reaches a visible result, the next action or reset behaves as intended, and the console has no errors. Then report and stop so the user can steer. Build the path from the opening screen to the first meaningful result. Add explicit must-haves and the highest-value alternate state next. Besides the milestone checkpoints in `prototype/checkpoints/`, save one before a risky revision. Reserve roughly the last 25–30 minutes for QA, polish and rehearsal, scaled to the time left.
- Write a one-line visual direction based on the game and the task, then choose the layout around the action. Use landscape for a game lobby or match HUD when it fits, portrait for a short player flow, and a wide workspace for comparison or operations. In the first viewport, show the current state and the next meaningful action. Use [UI guidance](references/ui-kit.md) to choose hierarchy, assets and feedback. [The scaffold](assets/scaffold.html) is optional for a simple select-and-confirm flow. Replace its sample mechanics and copy with the actual brief. For other flows, build directly and reuse only the parts that fit.
- Use deterministic seed data and ordinary controls to make the demo repeatable. Show pending, unavailable, completed, or failure states when they change the player's next action. Keep presentation notes outside the player interface by default. Add a reset or scenario switch only where needed to replay a state or demonstrate waiting or other players. Clearly label simulated live data, matchmaking, economy, or AI when it could be mistaken for a real connection. If the feature needs simulated AI, have its output respond to the current player data.
- Keep `index.html` easy to patch in later turns. Open it with a short comment that lists its sections, and keep labelled blocks in order: `/* == TOKENS == */`, `/* == LAYOUT == */`, `<!-- == SCREEN: name == -->`, `/* == DATA == */`, `/* == STATE == */`, `/* == RENDER == */`, `/* == ACTIONS == */`. Find the relevant blocks with `rg -n "== NAME"`, read the state and calls they depend on, edit the smallest range needed, and update the section list when you add a block.
- Keep the main state understandable and guard against duplicate rewards/actions when relevant. For persistence, use a versioned storage key and let the session work in memory if storage is unavailable. Prefer inline assets when an image is essential to the single-file demo. A playable Canvas mechanic is appropriate when the brief calls for real-time input or simulation.
- When there is a deadline, check the local time (`Get-Date` in PowerShell) before sizing a step, and compare it in the time zone written in `截止`; the remote machine's clock may use another zone. In the last 30 minutes, stop adding features and only fix, verify and prepare the demo.

## Verify, review and hand over

- Per turn, verify the behavior you changed. Run the full checklist once, at handover. Handover is done when every item in the BRIEF.md checklist has been checked on the actual page.
- Open the exact deliverable through `file://`. Follow the real controls from a fresh state to the result, exercise the most likely edge case, and replay after reset or reload as appropriate. Check the first screen at the presentation size, the intended player viewport and the browser console. Use [the QA checklist](references/qa-checklist.md) for specifics. If no browser tool can open the file, use headless Edge or Chrome from the shell rather than simulating the DOM in Node. Spend at most 5 minutes getting a browser path to work; then ask the user to click instead. In PowerShell: `mkdir prototype\qa -Force`, `$edge = "${env:ProgramFiles(x86)}\Microsoft\Edge\Application\msedge.exe"`, `$u = [System.Uri]::new((Resolve-Path prototype\index.html).Path).AbsoluteUri`, then `& $edge --headless=new --window-size=1280,800 --screenshot="$PWD\prototype\qa\shot.png" $u` and view the image. To check logic, copy the page to `prototype/qa/`, add an `error` listener as the first script in `<head>` and a script at the end that clicks the main path and writes the final state and errors into the DOM, then read it with `--dump-dom --virtual-time-budget=3000`. Report this as 逻辑检查: it can't show that a button is visible or clickable. Before marking the main path 已验证, have it clicked on the real page, by a browser tool or by asking the user to click a named path and describe what they see.
- Report the file path, what you actually verified, and the shortest click path. If the prompt requires a presentation, use [demo prompts](references/demo-script.md) to prepare a short talk track from the actual build. State the product hypothesis and relevant guardrail when they explain the design.
- When the user asks for a review (复查), add no features. Open the page with a browser tool or headless Edge, walk the demo path, and report findings ordered by demo impact: (1) breaks the demo, (2) confusing in the first 5 seconds, (3) the screenshot moment is weak or hidden, (4) if the feature has AI, it does not visibly respond to player data, (5) polish. Fix (1) and (2) straight away unless told otherwise. List the rest with a one-line fix each and wait for the user to choose.
